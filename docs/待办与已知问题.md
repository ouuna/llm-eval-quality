## 二、阻塞级问题（必须先解决）

### P0-1 检索是词频匹配 —— 召回率是最大瓶颈

**现状**
```python
# app/rag.py:207
def retrieve(question, docs, top_k=None):
    """检索：词组 + 同义词扩展 + 词长加权打分"""
```

**问题**
纯关键词打分 + 手写同义词表。实测召回率：
- smoke 集**50%**
- coverage 集**66.7%**

典型失败案例（`extended` 集）：
- `ext_sum_01`「请总结资料中关于「测试方法」的内容」
  → 召回的是「持续集成：代码提交后自动触发构建和测试」
  → 因为「测试」二字匹配上了，而真正该召回的四个测试方法都没命中

**为什么这是 P0**
召回 50% 意味着**一半的问题在检索阶段就失败了**，
后面所有评测器测的都是「模型基于错误上下文作答」，
测不出系统真实质量。

**建议做法**
1. 先做诊断：把召回失败与「RAG 系统本身能力差」区分开
   （当前指标混在一起，无法判断问题在检索还是生成）
2. 引入 Embedding 语义检索，与现有词频检索**并行**，
   用同一批 Gold Set 对比两者召回率
3. 混合召回：BM25 + 向量，取并集后重排

**注意**：加Embedding 会引入第三方依赖（目前是 0 依赖）。
权衡后决定，并在 README 说明。

### P0-2 Gold Set 循环论证 —— 结论有水分

**现状**
- 30 条样本的**题目、答案、标签、评测器的检测规则，全部出自同一作者**
- `eval/datasets/gold_set.py` 里仍内置 `SAMPLES` 常量作为兜底数据源

**问题**
评测器的检测规则是**为检出这批样本的缺陷而设计**的，
再用同一批数据验证它，结论天然偏乐观。
实测「Recall 100%」这个数字水分很大。

**建议做法**
1. **代码层面**：`SAMPLES` 兜底逻辑改为警告 ——
   文件不存在时应该明确提示「Gold Set 未配置，评测器指标不可用」，
   而不是静默用内置样本（静默兜底会让人误以为验证过了）
2. **流程层面**：
   - 找第二位标注者（同学/同事）独立标注 30 条
   - 计算 Cohen's Kappa 等一致性指标
   - 不一致的样本单独讨论——那些分歧恰恰是最有价值的
3. 如果找不到第二标注者，**在 README 里如实写明**
   「单标注者，评测器指标存在乐观偏差」

**当前 `eval/evaluators/validation.py` 无任何 IAA 相关代码。**

### P0-3 分支保护未生效 —— 门禁形同虚设

**现状**（截图确认）
- PR 上的检查已全部跑通（8 successful checks）
- 但分支保护页的 status checks 搜索框**始终空白**
  （显示 "No required checks"）
- 已试过：新建PR、重新触发、检查 workflow 存在性，均无效

**影响**
门禁只在 Actions 页面显示结果，**不影响 PR 能否合并**。
可以合并测试失败的代码。

**建议做法**
1. 优先试 **Repository Ruleset**（新版功能）：
   Settings → Rules → Rulesets → New ruleset → New branch ruleset
   在那里配置 required status checks
2. 若 classic rule 仍不行，检查是否需要
   `Require a pull request before merging` 先勾上
3. 兜底方案：用 `gh` CLI 或 API 创建规则
4. **无论哪种方式，先确认仓库是公开还是私有** ——
   私有仓库的某些保护功能可能受限

### P1-2 LLM Judge 未在 CI 启用

**现状**
- `eval/evaluators/judge.py` 实现了偏差控制：
  - `check_judge_consistency()`（刻度漂移检测，4 处引用）
  - `check_position_bias()`（位置偏好检测，4 处引用）
- 新增 `eval/judge_bias.py` CLI 工具，三类检测齐全
- **但 CI 里只作为 `workflow_dispatch` 的手动开关**：
  ```yaml
  if [ "${{ inputs.enable_judge }}" = "true" ]; then EXTRA="$EXTRA --judge"; fi
  ```
  默认 false，**从没在自动流程里跑过**

**问题**
1. `judge_bias.py` 的自检结果从未在 CI 呈现过
2. Judge 与被测系统同模型（`glm-4-flash`），**自我偏好风险未验证**
3. 偏差控制的代码写了但没在真实数据上验证过

**建议做法**
1. 先跑 `python -m eval.judge_bias` 拿到真实数据
2. 若检出偏差 → 换用更强的 Judge 模型，或明确文档说明「Judge 结果仅供参考」
3. 若未检出 → 接入 `regression.yml` 的 schedule job

### P2-2 README 的召回率数字不准

**README 第 388 行写「实测召回率约 82%」**，
但实测：
- coverage 集 **66.7%**
- smoke 集 **50%**

82% 那个数字来自更早的测量，检索逻辑后来改过。

**建议**：改为区间并说明来源，例如
「实测召回率 50%~67%（取决于数据集）」。
或加测试绑定（`test_readme_honesty.py` 已有此类机制）。

### P2-3 数据集 74 条，需求要求 50~100 条

严格说达标，但**分布不均**：
- `multi_hop`（多跳）仅 1 条（full集）
- `paraphrase` 仅 2 条

单条用例只能说明「这类问题里的一种」，覆盖面不足时
某个细分类目的真实表现完全测不出来。

**建议**：优先补充 `multi_hop` 与 `context_conflict`
（这两类在 coverage 集表现最差：多跳 50%、对比 40%）

## 五、工程问题

### P3-1 无测试覆盖率统计

没装 `pytest-cov`，不知道 729 个测试实际覆盖了多少代码路径。

**建议**：
```bash
pip install pytest-cov
pytest --cov=eval --cov=app --cov-report=term-missing
```
先看数字，再决定补哪些测试。**不要为了提高数字而写无意义的测试。**

### P3-2 `simulate_ci` 在 CI 上失败过，暂设为不阻断

`tests/simulate_ci.py` 在 CI 上失败过两次，本地（含Python 3.13）都能跑通，
无法定位。已设为 `continue-on-error: true`。

**问题**：这个工具现在**只在本地有用**，CI 上失败也不会有人知道。

**建议**：要么定位根因，要么在 README 明确标注
「该工具在 CI 上不保证可用，仅供本地使用」。

### P3-3 上下文冲突检测能力有限

只支持「冒号型」句式。否定型冲突（`A关注Y` vs `A完全不关注Y`）
因主体抽取依赖 SVO 语序而漏检。

已在 `tests/negative/test_negative.py` 中如实标注为已知局限，
但**能力本身没有改进**。

**建议**：如果实际场景会遇到否定型冲突，
需要引入依存分析或规则增强；否则在README 明确
「本系统不处理否定型冲突，检测到时应人工复核」。
