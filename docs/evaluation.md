# 评测方法说明

> 回答"这个系统怎么工作、为什么这么设计、怎么证明它可靠"。

---

## 一、为什么要做自动评测

大模型（RAG 问答系统）的输出**无法用传统方式判断对错**。

传统测试：点按钮 → 断言弹窗文案
AI 测试：问一个问题 → 得到一段自然语言 → **怎么断言？**

三个根本困难：

1. **输出是概率性的** —— 同一问题两次回答可能不同
2. **判据是语义化的** —— "答得对不对"不是字符串匹配能解决的
3. **失败形态特殊** —— 最严重的不是"答错"，而是"**一本正经地编造**"

因此必须建立量化机制，把"我觉得答得还行"变成"幻觉率 3%、拒答率 98%"。

---

## 二、评测链路

```
数据集 Dataset
    ↓
① 调用被测系统 → 得到 answer + contexts + latency + token
    ↓
② 三态检查：Provider 报错了吗？
    ├── 是 → status=ERROR，绝不当成通过
    └── 否 ↓
③ 声明级幻觉检测
    ↓
④ 正确性 / 完整性 / 相关性 / 拒答判定
    ↓
⑤ 汇总指标
    ↓
⑥ Quality Gate 分层判定
    ↓
⑦ 报告 + 基线对比 + CI 阻断
```

---

## 三、核心设计：三类用例

这是整个评测体系的基石。

| 类型 | 场景 | 期望行为 | 考察目标 |
|---|---|---|---|
| `in_domain` | 知识库内有答案 | 准确作答 | 检索召回 + 答案正确 |
| `out_domain` | 知识库中**无答案** | **必须拒答** | **幻觉抑制（核心）** |
| `ambiguous` | 问题不完整 | 要求澄清 | 避免强行作答 |

**为什么必须有域外用例？**

只测域内的话，AI 答对了你误以为没问题。**幻觉只在模型没资料时才暴露。**

举例：问「北京有哪些好吃的火锅店」，知识库没这条内容。普通 LLM 会热情推荐海底捞、呷哺——**这在通用测试里看起来是"正常回答"，但它完全是编的。**

## 四、幻觉检测：为什么是声明级

### 旧方法的问题

字符覆盖率：

```python
coverage = |answer实词 ∩ context实词| / |answer实词|
```

**实测结果：5 个幻觉场景全部判为"无幻觉"**

| 回答 | 上下文 | 覆盖率 | 旧判定 | 正确判定 |
|---|---|---|---|---|
| 中国的首都是**上海** | 北京是中国的首都 | 1.00 | 无幻觉 ❌ | **有幻觉** |
| 分为基础层、用例层、**报告层** | …数据层 | 0.71 | 无幻觉 ❌ | **有幻觉** |
| 由 **Kent Beck** 提出 | …修改代码后 | 0.44 | 无幻觉 ❌ | **有幻觉** |
| 今天**天气晴朗 25 度** | 等价类划分 | 0.00 | 无幻觉 ❌ | **有幻觉** |

**根因：字符覆盖率不区分实词的"角色"。**"上海"和"北京"在字符层面都是中文词，无法分辨哪个是正确的。

### 新方法

```
Step 1  拆声明：把回答拆成原子事实
Step 2  逐条验证：每条声明是否有上下文依据
Step 3  叠加检查：forbidden / 数字冲突 / 否定冲突 / 拉丁冲突
Step 4  跑题检测：全部声明与上下文零重合 → 判幻觉
```

**关键：把"整段"的问题降级为"逐句"的问题。** 任何一条声明无依据，整条回答就有幻觉。

### 修复历程

| 版本 | 幻觉率 | 问题 |
|---|---|---|
| 整句精确匹配 | 71% | 改写一个字就误判 |
| 实词覆盖率 | 7% | 仍漏实体调换 |
| + forbidden_facts | 7% | 依赖预标注 |
| + 数字/否定/拉丁冲突 | **0% 漏报** | 能力边界见下 |

## 五、正确性：为什么不能只看幻觉

**幻觉检测只能回答"有没有编造"，不能回答"答得对不对"。**

反例：

```
问题：  自动化测试框架分为哪几层？
回答：  分为基础层、用例层。        ← 漏了数据层
上下文：基础层、用例层、数据层
```

说的都是上下文里有的，**没有幻觉**。但答案不完整、可能误导用户。

所以必须有独立的正确性指标，以 `required_facts` 覆盖率判定。

**指标间自洽性检查**能发现这类问题：

```
域内准确率 100%
平均相关性 0.51        ← 矛盾
```

**两个指标不自洽，说明至少一个定义错了。** 这是审计阶段最有用的自证手段。

## 六、相关性：修正一个方向性错误

### 错误实现

```python
# |question_chars ∩ answer_chars| / |question_chars|
```

测的是"答案有没有抄问题里的字"。

| 问题 | 回答 | 旧分数 | 实际质量 |
|---|---|---|---|
| 如何提高代码质量？ | 代码质量的提高方法 | **1.0** | 废话 |
| 如何提高代码质量？ | 提高代码质量需遵循规范 | 0.4 | **正确答案** |

**完全无关的回答只要复述问题词就能满分。**

### 修正

```
Level 1  required_facts 覆盖率   ← 测"有没有答到被问的东西"
Level 2  answer ↔ reference 语义
Level 3  answer ↔ context（降级，显式标注）
```

## 七、三种评测方法的分工

| 方法 | 擅长 | 不擅长 | 成本 | 定位 |
|---|---|---|---|---|
| **Lexical** | 确定性、字面比对 | 同义改写、实体调换 | 零 | Baseline |
| **Semantic** | 同义改写 | 粒度粗、无法定位声明 | 中 | 辅助 |
| **LLM Judge** | 复杂语义 | 有偏差 | 高 | 交叉验证 |

**三者不合并成一个分数。** 各自独立记录，因为它们的失效模式不同。

### 实测分歧（证明词级方法失效）

| 场景 | Lexical | Semantic | 分歧 |
|---|---|---|---|
| 同义改写 | 0.474 | 0.812 | 0.338 |
| 说错层 | 0.353 | 0.767 | 0.414 |

**4 个场景出现结论相反**——这说明单一方法的结论不可信。

### 但语义也不是万能

```
"多出一层业务层"：语义 0.773
"完全正确答案"  ：语义 0.794
```

**语义层面区分度不够。** 真正能定位到"业务层"这条声明的，只有声明级验证。

## 八、怎么证明评测器本身可靠

这是整个项目最难的问题，因为存在**循环论证**风险：
用自动评测器验证自动评测器，必然得出"100% 准确"。

### 三层验证

**第 1 层：Gold Set 反向测量**
30 条人工标注样本 → 计算 Precision / Recall / F1 / FPR / FNR

**第 2 层：变异测试（最严格）**
故意把数据改坏，看评测器能否发现：

```
变异类型           检出
实体调换           ✓
数字篡改           ✓
答案替换           ✓
追加伪事实         ✓
```

**如果人为注入的缺陷都发现不了，对真实缺陷的检出率也不可信。**

**第 3 层：回归测试**
16 条历史缺陷固化为测试，任何修复回退都会立即失败。

### 当前实测结果与局限

```
Accuracy   96.7%
Recall     100%
FPR         6.2%
```

**但这个结果存在循环论证**：样本是我写的，标签也是我标的。

**真实的可靠性验证需要**：
1. 他人撰写的答案
2. 至少两人独立标注
3. 200+ 样本

**这是本项目最重要的未完成项。**

## 九、质量门禁：阈值之外的诊断

门禁失败必须能回答三个问题：
1. **哪个指标失败** —— 名称与层
2. **差多少** —— 当前值 vs 阈值 vs 幅度
3. **怎么修** —— 修复方向

```
[answer_correctness] 未达标：0.8500 >= 0.9
失败样本：case-01, case-02, case-03

修复方向：
  answer_correctness: 完善 required_facts 标注；检查被测系统 Prompt
```

**只说"不达标"的门禁等于没有门禁** —— 开发者不知道为什么改，改完也不知道有没有改对。

## 十、性能与成本

| 指标 | 说明 |
|---|---|
| `p95_latency_ms` | 95 分位延迟 |
| `avg_cost` | 平均成本（估算） |

**API 未提供 token 时记 `unavailable`，不填 0。** 填 0 会让均值看起来比实际便宜，违反"不要伪造数据"。

## 十一、持续集成策略

| 触发 | 数据集 | 目的 |
|---|---|---|
| PR | smoke | 合并前快速反馈 |
| push main | smoke + full | 合并后全面回归 |
| 定时（每日） | full | 检测环境或依赖变化 |
| 手动 | 可选 | 发版前验证 |

**无 API 密钥时明确跳过真实评测，而非假装成功。** 同时离线测试（Mock 模式）仍会执行，保证评测框架本身持续被验证。

## 十二、端到端示例

### 1. 一个成功的评测

```bash
$ python -m eval run --dataset smoke

Quality Gate: PASSED
  总体通过率 100%
  幻觉率 0%
  域外拒答率 100%
```

### 2. 一个故意制造的失败

把被测系统的 Prompt 改成无防幻觉约束：

```bash
$ python -m eval run --dataset smoke

Quality Gate: FAILED
  [refusal_accuracy] 未达标：0.6250 >= 0.95
  失败样本：smoke_out_01, smoke_out_02, smoke_una_01
```

**门禁在 CI 中会阻断合并。**

### 3. 回归保护

```bash
$ python -m pytest tests/regression/ -q

24 passed, 9 xfailed
```

`xfailed` 明确标记"这 9 条不由声明级验证覆盖"——**不假装通过**。
